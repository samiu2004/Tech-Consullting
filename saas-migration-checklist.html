SaaS Migration Checklist: Test the Data Before You Switch

Use an export manifest, acceptance tests and a rollback decision before moving production work.

A successful import count does not prove that a business can still use its data. Records may arrive while important relationships, files, history or permissions do not. Migration is an acceptance task as much as a copying task.

This checklist is for a team that has already selected a replacement. It is a planning framework, not a tool-specific guarantee. Use a qualified specialist when the sensitivity, scale or complexity exceeds the team's ability to verify the result.

Name the owners and the dependencies

Assign a business owner who decides whether the new setup is acceptable and a technical owner who manages the transfer. Identify the people who use the data and the systems that read or write it.

List forms, scheduled jobs, reports, email connections and any client-facing integrations. A record migration can appear complete while an old form continues sending new enquiries to the retired system.

Write an export manifest

Item What to document
Records Types, counts, required fields and identifiers
Relationships How linked records remain connected
Files and history What is exportable and what is excluded
Owners and permissions Who should access and change information
Integrations Inputs, outputs, credentials and responsible owner
Retention What must be kept under the business's actual requirements

Keep a recoverable copy through the organization's approved process. Test that it can be opened and interpreted. An export you cannot read or map is not a sufficient recovery plan.

Map and test a representative sample

Choose a sample that includes ordinary records and difficult cases: missing values, duplicate identifiers, multiple relationships and large or unusual attachments. Map the destination fields and record any conversion rule.

Import the sample into an appropriate test space. Compare counts, field values and relationships. Ask users to complete the tasks the new system must support. Check that permissions restrict access as intended; importing data into the correct account does not automatically establish correct visibility.

Define acceptance before cutover

Write pass/fail criteria with the business owner. Examples include all critical open items having an owner, representative relationships resolving correctly and required reports matching an agreed reconciliation method. Use your actual tolerances rather than an arbitrary universal error percentage.

List known exclusions and obtain approval. If important information cannot transfer, decide how it will remain accessible and whether that arrangement is acceptable. Do not treat an unexpected loss as a formatting issue simply to meet a deadline.

Plan the production change

Set a cutover window, a communication plan and a rule for changes made during the move. Decide whether work pauses, continues in one system or requires reconciliation afterward. Keep the authoritative system clear.

Transfer the approved data, reconnect dependencies and run the acceptance checks again. Record the result before giving everyone access. Keep a named owner available to handle early problems rather than treating go-live as the end of the task.

Set a rollback decision point

Decide in advance which failures require returning to the old setup, who can authorize that decision and how changes made since cutover will be reconciled. A rollback is not simply restoring an old file if people have already added new work elsewhere.

Do not cancel old access until the approved acceptance and recovery conditions are met. Check the contract's notice and overlap cost early so a safe transition does not create an unexpected billing dispute.

Monitor and close the migration

Review the first real forms, scheduled jobs, reports and user tasks. Confirm that no process still writes to the retired system. Remove temporary access and transfer administration to the ongoing owner.

Use the cancellation checklist for the final billing and data-access steps. Keep the manifest, acceptance record, exclusions and decisions together. They explain what moved, what did not and who accepted the new operating state.
